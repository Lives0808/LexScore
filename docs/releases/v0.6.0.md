## LexScore v0.6.0 — 拍照批改

纸面作文不用再手打：**拍一张照片就能进批改流程**。

### 完整链路

```
拍摄 / 相册选图
   ↓  读取并摆正（EXIF 方向）
自动找纸边（Otsu 阈值 + 四角极值点）
   ↓  四点可手动微调
透视矫正（求解单应矩阵，四角各自对齐）
   ↓
去阴影增强（背景除法 + 对比度拉伸）
   ↓  擦除笔刷 / 框选擦除，抹掉涂改痕迹
离线 OCR（ML Kit 拉丁文字识别）
   ↓  自动重组段落
填入作文输入框 → 走原来的四维批改
```

### 每一步做了什么

**自动找纸边** —— 纸张通常是画面里最大的一块亮区。用 Otsu 自适应阈值二值化后，
取该区域的四个极值点当作四角。亮区占比不合理时（背景太亮 / 没拍到纸）
退回整幅内缩，交给用户手动调整，不会给出一个明显错误的结果。

**透视矫正** —— 不是简单旋转，是求解单应矩阵把四个角各自对齐。
斜着拍、纸面有透视变形都能拉正。直接解「目标矩形 → 原图四边形」的映射，
每个输出像素正向查表，省掉一次矩阵求逆。

**去阴影** —— 用「背景除法」而不是固定阈值：
先大幅降采样再模糊，得到只保留光照趋势的背景图，原图除以背景图，
光照被归一化，手影和明暗渐变一起消失。比固定阈值抗干扰得多。

**手动清理** —— 擦除笔刷与框选擦除，用来抹掉涂改痕迹、老师批注、
多余的线条，只保留作文正文。支持撤销，可以随时切回原图对比。

**OCR 与分段** —— ML Kit 的模型**打包在 APK 里**，识别全程在本机完成，
图片不会上传到任何服务器。识别结果会按句末标点重组段落，
而不是把 OCR 断开的每一行都变成一段。

> **一个反直觉的发现：去阴影后的图反而不适合喂给 OCR。**
>
> A/B 实测同一张图：
>
> | 输入 | 结果 |
> | --- | --- |
> | 矫正后的原图（带轻微光照不均） | **100% 正确**，零错误 |
> | 去阴影 + 对比度拉伸后 | `frce` / `cducation` / `Alhough` 三处误识 |
>
> 原因是**对比度拉伸抹掉了灰色抗锯齿边缘**，而 ML Kit 的模型正是靠这些
> 灰阶渐变来分辨 `e` 与 `c`、`f` 与 `t` 这类形状相近的字母。
> 把边缘压成纯黑纯白，等于把模型的判别依据删掉了。
>
> 所以最终实现是：**OCR 永远跑矫正原图，增强只作为「给人看」的辅助**
> （用户需要肉眼确认和涂抹擦除时，白底黑字更好操作）。
> 用户的擦除笔迹会同时烘进 OCR 的输入，保证抹掉的痕迹不会进识别结果。

### 实测数据

在 Android 15 模拟器上用一张模拟拍摄的作文照片（1500×2100，倾斜 3.5°，
带光照渐变与纸张投影）跑完整链路：

| 阶段 | 结果 | 耗时 |
| --- | --- | --- |
| 读取并摆正 | 1214×1700 | 417 ms |
| 自动找纸边 | 四角与纸张边缘吻合 | 200 ms |
| 透视矫正 | 999×1421，纸面完全拉正 | 490 ms |
| 去阴影增强 | 背景纯白，文字清晰 | 114 ms |
| OCR 识别 | 149 词，段落结构正确 | 230 ms |
| **合计** | | **约 1.5 秒** |

### 已知限制

- OCR 对印刷体效果好；**手写体识别率明显下降**（ML Kit 拉丁模型主要针对印刷体）
- 识别结果允许在界面上直接修改，确认后再填进输入框
- 极端光照（强反光、深阴影）下自动找纸边可能失准，可以手动拖四角
- 图片处理全部在内存完成，超大图（>2000px）会先降采样到 1700px

### 顺带修的 bug

`detectDocumentQuad` 误用了会回收源图的缩放函数，导致后续透视矫正
抛 `Can't call getPixels() on a recycled bitmap`。已拆成两个函数：
`scaleCopy`（不回收）给「只看一眼」的场景，`scaleToMax`（回收）给确实要替换的场景。
